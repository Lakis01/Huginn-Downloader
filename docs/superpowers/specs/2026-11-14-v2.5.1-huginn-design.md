# Huginn Downloader v2.5.1 — Design

## Intent

Ship a compatible v2.5.1 update that works with externally installed `yt-dlp`, uses localized desktop folders, reports version age without blocking downloads, avoids unnecessary tagging work, and rebrands the visible Firefox project as **Huginn Downloader**.

## Goals

- In the GUI-launched Linux host, move existing `~/.local/bin` then `/usr/local/bin` entries to the front of `PATH`, deduplicating entries, so the selected `yt-dlp`, `ffmpeg`, `ffprobe`, `rsgain`, and Python match the user's environment. The apt helper prepends the invoking user's `~/.local/bin` for its command probes.
- Make apt dependency setup inspect `yt-dlp`, `ffmpeg`/`ffprobe`, `python3`, Python `mutagen`/Pillow imports, and optional `rsgain` before installing anything; skip `apt-get update`, sudo, and install entirely when all requested dependencies are present. The helper is used by `install.sh --install-deps` and shipped at `/usr/lib/firefox-youtube-downloader/install-apt-deps.sh` in the `.deb`; package users run it without sudo so it can inspect their normal `PATH`, then it invokes sudo only if packages are missing.
- Debian package metadata: `Depends: python3`; `Suggests: yt-dlp, ffmpeg, python3-mutagen, python3-pil, rsgain`. Fedora RPM uses `Requires: python3` and `Suggests: yt-dlp, ffmpeg-free, python3-mutagen, python3-pillow, rsgain`. DNF's default weak-dependency installation covers Recommends/Supplements, not Suggests. Arch keeps `python` in `depends` and lists `yt-dlp`, `ffmpeg`, `python-mutagen`, `python-pillow`, and `rsgain` under `optdepends`. No media executable or tagging library is a hard package dependency because distro package databases cannot recognize arbitrary binaries/modules installed outside their package databases.
- Use XDG Music, Videos, and Downloads directories on Linux with this precedence: explicit `XDG_MUSIC_DIR`/`XDG_VIDEOS_DIR`/`XDG_DOWNLOAD_DIR` environment value, then the matching assignment in `$XDG_CONFIG_HOME/user-dirs.dirs` (or `~/.config/user-dirs.dirs` when unset/empty), then English `~/Music`, `~/Videos`, or `~/Downloads`. Parse without sourcing/evaluating shell code; accept quoted assignments and expand `$HOME`, `${HOME}`, and `~`; ignore invalid relative paths. Normalize only old default presets (`~/Music/Youtube Downloads`, `~/Videos/Youtube Downloads`, `~/Downloads/Youtube`): preserve them if the target directory contains any entry (including hidden files), or if checking it fails; otherwise use the localized XDG path. Leave custom config paths unchanged.
- Treat an outdated `yt-dlp` version as a warning, never as a gate. Before an attempt, inspect the installed executable against the 24-hour GitHub-latest cache and stale-age threshold offline; do not add a network wait before downloading. Always run the selected download. On failure, refresh status and say an outdated version may have contributed, with the update hint.
- Re-check persisted `auto_tag` immediately before post-processing only for downloads started from live config: a true-to-false change skips Mutagen/copy work and removes generated tag/thumbnail sidecars; false-to-true mid-download stays false because required data was not fetched. If long-audio routing needs duration fallback, retain `.info.json` until the route is chosen, prefer printed duration, then clean it. Skip tag-copy only when all of `title`, `artist`, `album`, `date`, composer/lyricist/producer/arranger/conductor/engineer/performer/instrument credits, publisher, ISRC, genre, recording date, studio are empty **and** there is no local cover. Preserve the downloaded media and normal routing/ReplayGain behavior. Keep full `.info.json` for rich descriptions; do not add a second `tags.json` format without measured gains and tests.
- Shorten codec labels, explain encoding behavior in the README, and place forced Opus last.
- Rebrand visible product, extension, toolbar/context-menu and desktop text, raven icon, release asset basenames, and repository to **Huginn Downloader** / `Huginn-Downloader`. Preserve the existing Firefox Gecko ID, Native Messaging host ID, config paths, system install paths, and OS package identifiers so v2.5.0 installations upgrade in place. Internal package names remain stable while release filenames use Huginn branding.
- Keep `browser_specific_settings.gecko.id` at `firefox-youtube-downloader@lakis01.github.io`; this is an update to the existing Unlisted AMO add-on, not a second add-on. Keep the Native Messaging `name`, manifest filename, `allowed_extensions`, `/usr/lib/firefox-youtube-downloader`, `/usr/lib*/mozilla/native-messaging-hosts`, Windows `FirefoxYouTubeDownloader` app-data path, config namespaces, desktop-entry filenames, and OS package `Package`/`Name`/`pkgname` stable; only visible strings, repository/source URLs, and release asset basenames change. Update `homepage_url` to the renamed repository. The raven is an original silhouette icon in the incumbent red rounded-square field.
- README states that both the Firefox extension and local companion are required; Huginn Downloader is a graphical frontend that connects YouTube watch controls/context menu to the local companion, while yt-dlp performs extraction/download. Explain Python 3 (Native Messaging host), yt-dlp (backend), FFmpeg (merge/conversion/cuts), Mutagen and Pillow (automatic audio tags/artwork; useful with auto-tag enabled), and optional rsgain (ReplayGain). Tell users to pin the extension to the toolbar for one-click settings; record CachyOS+KDE, LMDE 7+Cinnamon, and Debian 13+GNOME as tested so far.
- Release asset basenames are `huginn-signed.xpi`, `huginn-companion_2.5.1_all.deb`, `huginn-companion-2.5.1-1.noarch.rpm`, `huginn-downloader-2.5.1-source.tar.gz`, and `huginn-downloader-2.5.1-arch-pkgbuild.tar.gz`; internal package IDs remain `firefox-youtube-downloader-companion`.
- Repository rename occurs before package validation so PKGBUILD/source URLs target the canonical `Huginn-Downloader` URL. GitHub redirects the old URL, but update repo links and the local `origin` explicitly.
- Keep signing explicit. Do not store AMO credentials in the repository or release assets. The previous legal assessment was not a guarantee: README must not claim that using yt-dlp or being a frontend removes copyright/anti-circumvention liability.
- No legal immunity is asserted: the frontend/backend separation, user consent, or a README disclaimer does not by itself decide liability under German copyright/anti-circumvention law. README describes product behavior factually and may remind users to use downloads only when permitted; detailed legal advice remains with qualified German counsel.

## Approaches

1. **Compatibility-first update (chosen).** Keep machine-facing IDs/package identities stable, change human-facing names and release artifact names, and teach package helpers to recognize already-present tools. This allows existing v2.5.0 installs to receive v2.5.1 while fixing LMDE's stale apt `yt-dlp` case.
2. **Full identifier reset.** Rename the extension ID, Native Messaging host ID, config namespace, package IDs, and install paths to Huginn. This would present a clean slate but would create a second Firefox add-on identity and require explicit migration/uninstall logic; it conflicts with the user's smooth-upgrade requirement.
3. **Keep the existing branding and only patch dependencies.** Lowest release risk, but ignores the requested Huginn identity, raven icon, and updated onboarding copy.

The user selected the v2.5.1 implementation and chose the visible name **Huginn Downloader** after being informed of the existing `huginn/huginn` automation project. Exact internal compatibility identifiers remain legacy implementation details, not displayed branding.

## Release Gate

Push the merged v2.5.1 code to the current repository, rename it to `Huginn-Downloader`, and update the local `origin` URL before package validation. Run the manual workflow on the renamed repo's `main` and inspect the actual `.deb`, RPM, and Arch recipe before signing. Do not change source commits after validation: the annotated `v2.5.1` tag must point to that same `main` commit. Sign the XPI through the existing `--channel=unlisted` flow using the exported environment credentials (never print or persist values), push the tag, create a draft release with the signed XPI, let the tag workflow rebuild and attach packages, verify all five assets, then publish.
